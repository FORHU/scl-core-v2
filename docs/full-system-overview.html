1. What is chat-wonder-v2-api?

chat-wonder-v2-api is not a chatbot. It is an AI decision engine — a FastAPI server that accepts a question from another application, reasons about it (potentially using external tools), and returns an answer. The calling application owns the user interface; chat-wonder owns the intelligence.

Current clients of chat-wonder-v2-api:

  • mirror-app — StyleOS Smart Mirror (Orange Pi 5 Pro hardware), AI-powered fashion and personal styling, built for live hardware demo at VivaTech 2026
  • law-ph — Philippine legal AI assistant (Next.js), retrieves and interprets Philippine statutes using pgvector semantic search
  • At least 3 additional apps not currently in the workspace, also scheduled for VivaTech 2026 demo
Why this distinction matters for XAI Because chat-wonder makes autonomous decisions that directly affect end users in high-stakes domains (legal advice, medical advice, financial decisions), the EU AI Act classifies these as high-risk AI systems — which require that affected individuals receive meaningful explanations of why the AI made each decision. A chatbox used for entertainment does not.

2. The EU AI Act Problem — Why Explainability Matters

The European Union AI Act, which came into force in 2024 and is being phased into enforcement through 2026, requires that AI systems used in high-stakes contexts provide explainability — the ability for affected individuals and regulators to understand why the AI produced a given output.

This is not optional and not soft: it is a regulatory compliance obligation with fines.

The law's requirements, translated to our system:

  1. Transparency — When the AI decides to retrieve a legal document, call a weather API, or search the web, there must be a recorded reason for that decision in the AI's own words, not a post-hoc reconstruction by a different system.
  2. Auditability — The reasoning trail must be observable and preservable, not just a live console log.
  3. Authenticity — The explanation must be the AI's genuine reasoning at the moment of the decision. An explanation written after the fact by a separate LLM call ("what might this AI have been thinking?") is legally equivalent to a fabrication and would fail compliance review.
Critical compliance boundary Options that use a background thread to generate a plausible-sounding explanation after the AI has already made its decision are NOT XAI-compliant. They produce text that describes what the AI could have been thinking, not what it was thinking. This approach was considered and rejected for this system.

This is why the glass-box tracer was built — and why Option 2 (chain-of-thought, described in Section 9) is the only acceptable approach for capturing the AI's reasoning.

3. What is SCL? — Supervised Cognitive Loop

SCL (Supervised Cognitive Loop) is the observability and XAI compliance framework built alongside chat-wonder-v2-api. It consists of two components:

  • Instrumentation inside chat-wonder-v2-api — A function called broadcast_trace() is called at each significant decision point inside the AI loop. It records what the AI was doing and why, with zero impact on the AI's actual response.
  • scl-core-v2 — A separate FastAPI server that subscribes to chat-wonder's event stream, relays those events to browser clients, and serves the Glass-Box Tracer UI.

Together, these two components give a real-time, unfiltered window into every decision the AI makes during a chat turn — before it returns an answer to the calling application.

4. The R-CCAM Cognitive Loop — Stage by Stage

Every chat request that enters chat-wonder-v2-api is processed through a pipeline we call the R-CCAM loop: Request → Cognition → Control → Action → Memory, with a Retrieval step before the first Cognition cycle.

⬤ REQUEST

A new chat turn has arrived. Records session ID and the first 120 characters of user input. This is the entry point for every /chat and /chat-stream call.

◎ RETRIEVAL

RAG (Retrieval-Augmented Generation) results injected into the LLM context. If embeddings are loaded, reports which documents were retrieved and their relevance scores. Lists all available tools before reasoning begins.

◈ COGNITION

The LLM is reasoning. Reports each cycle number, the tool the LLM proposed to call (including the tool's description), the arguments it constructed, and the final text produced when no more tool calls are needed.

▣ CONTROL

The loop's decision point. Either APPROVED (tool call is new — proceed), BLOCKED (duplicate call with same args — inject reminder), or HITL GATE (human approval required — loop pauses and waits for /approve-tool).

▶ ACTION

The approved tool is actually executed. Reports "Executing…" before the call and the full result (up to 300 chars) after. This is the only stage where real-world side effects can occur (web search, API calls, database queries).

◉ MEMORY

After each tool result, the fact is stored in the LLM message context as a [Memory Fact] system message. All future reasoning cycles in the same turn treat this as ground truth and will not re-call the same tool with the same args.

The loop repeats Cognition → Control → Action → Memory up to 7 times (max_chains=7) or until the LLM produces a final text response instead of a tool call. Then the answer is returned to the calling application.

Legal AI path — different loop

When a query is prefixed with [legal ai], the system routes directly to a single-pass legal RAG pipeline — it does not use the tool loop. The AI performs a pgvector semantic search against the Philippine law corpus, then synthesizes an answer in one LLM call. This path emits REQUEST, RETRIEVAL, and COGNITION events but no CONTROL, ACTION, or MEMORY events (because there are no tool calls). Separate XAI coverage for this path is planned but not yet implemented.

5. How broadcast_trace() Works — Zero-Overhead Event Dispatch

The key design requirement: the tracer must not slow down chat-wonder-v2-api's response to the calling application. The solution is broadcast_trace(), a function that pushes an event to an in-memory asyncio queue in microseconds — with no network calls, no disk I/O, and no blocking.

Source: the_server.py lines 142–187

# the_server.py — line 140
_trace_queues: set = set()            # one asyncio.Queue per SSE subscriber

def broadcast_trace(event_type: str, text: str, session_id: str = None):
    data = json.dumps({
        "type":       event_type,       # request|retrieval|cognition|control|action|memory
        "text":       text.strip(),
        "session_id": session_id,
        "ts":         time.time(),      # Unix timestamp for ordering in UI
    })
    def _put_all():
        for q in list(_trace_queues):
            try:
                q.put_nowait(data)            # non-blocking; drops event if queue full
            except asyncio.QueueFull:
                pass                         # never block the LLM thread
    try:
        loop = asyncio.get_event_loop()
        if loop.is_running():
            import threading
            if threading.current_thread() is not threading.main_thread():
                loop.call_soon_threadsafe(_put_all)   # safe cross-thread delivery
                return
    except RuntimeError:
        pass
    _put_all()

Why call_soon_threadsafe is necessary

The LLM reasoning loop (both run_function_chain and streaming_run_function_chain) runs in a thread-pool worker, not the main asyncio event loop thread. asyncio queues are not thread-safe. If a worker thread calls q.put_nowait() directly while the event loop thread is reading the same queue, the result is undefined behavior. loop.call_soon_threadsafe() schedules the put operation to execute on the event loop thread at its next available moment — eliminating the race condition.

The SSE endpoint — chat-wonder's side

Source: the_server.py lines 168–187

# the_server.py — line 168
@app.get("/trace-stream", summary="Glass-box SSE — consumed by scl-core-v2")
async def trace_stream():
    async def _generator():
        q = asyncio.Queue(maxsize=200)
        _trace_queues.add(q)         # register this subscriber
        try:
            yield 'data: {"type":"connected"}\n\n'
            while True:
                try:
                    data = await asyncio.wait_for(q.get(), timeout=25)
                    yield f"data: {data}\n\n"
                except asyncio.TimeoutError:
                    yield 'data: {"type":"ping"}\n\n'  # keep-alive
        except asyncio.CancelledError:
            pass
        finally:
            _trace_queues.discard(q)    # clean up on disconnect
    return StreamingResponse(_generator(), media_type="text/event-stream",
        headers={"Cache-Control": "no-cache", "Access-Control-Allow-Origin": "*"})
Design note: one subscriber, not many This endpoint in chat-wonder-v2-api is not intended for browser clients. Only one entity ever subscribes to it: the scl-core-v2 tracer server. That keeps chat-wonder's subscriber set tiny (almost always 1 queue) while scl-core-v2 handles fan-out to however many browsers are open.

6. The Relay Architecture — scl-core-v2 and the Browser

scl-core-v2's tracer server (scl_tracer_server.py) does three things:

  1. On startup, launches a background task that subscribes to chat-wonder's /trace-stream
  2. Forwards every event from that upstream stream into its own set of asyncio queues
  3. Serves those events to browser clients via its own /trace-stream endpoint

Source: scl_tracer_server.py (full file)

# scl-core-v2/scl_tracer_server.py

CHAT_WONDER_TRACE_URL = "http://127.0.0.1:8000/trace-stream"
_trace_queues: set = set()

async def _relay_from_chat_wonder():
    """Permanent background task. One upstream connection, N browser fans-out."""
    while True:
        try:
            async with httpx.AsyncClient(timeout=None) as client:
                async with client.stream("GET", CHAT_WONDER_TRACE_URL) as response:
                    async for line in response.aiter_lines():
                        if not line.startswith("data: "):
                            continue
                        payload = line[6:]          # strip "data: " prefix
                        for q in list(_trace_queues):
                            try:
                                q.put_nowait(payload)
                            except asyncio.QueueFull:
                                pass
        except Exception:
            await asyncio.sleep(3)   # auto-reconnect on any failure

@app.on_event("startup")
async def startup():
    asyncio.create_task(_relay_from_chat_wonder())

@app.get("/")
async def serve_tracer():
    html_path = Path(__file__).parent / "run_glass_box_tracer.html"
    return HTMLResponse(html_path.read_text(encoding="utf-8"))

Why scl-core-v2 holds the /trace-stream, not chat-wonder

An earlier design had browsers connecting directly to chat-wonder's /trace-stream. This had two problems:

  • Browser security block — Opening the tracer HTML directly from the filesystem gives the page a null (file://) origin. Browsers block SSE connections from null origin pages even when the server sends Access-Control-Allow-Origin: * in some configurations.
  • Wrong load distribution — If 10 browsers are watching the tracer simultaneously, chat-wonder would hold 10 open asyncio queues and deliver every event 10 times. The relay pattern means chat-wonder holds exactly 1 queue regardless of how many browsers are connected.

With scl-core-v2 serving the HTML at http://127.0.0.1:8004/, the browser page has an HTTP origin and connects to the SSE stream on the same host and port — no CORS issue. chat-wonder holds one persistent subscriber (scl-core-v2); scl-core-v2 handles fan-out to all browsers.

7. Complete Data Flow: One Chat Turn, End to End

This section traces a single query — "What's the weather in Manila?" — from entry to output, showing exactly what happens in each system at each step.

Step 1 — Client sends the request

mirror-app (or law-ph, or any client) sends a POST to chat-wonder-v2-api: 

POST http://<chat-wonder>:8000/chat-stream
{
  "user_input": "What's the weather in Manila?",
  "session_id": "abc12345-..."
}

Step 2 — REQUEST broadcast (the_server.py line 903)

broadcast_trace("request", f"New turn — session {session_id} — input: {user_input[:120]}", session_id)

This is the very first line of the /chat and /chat-stream handlers, before any processing. The event is pushed to the trace queue immediately.

Step 3 — Persona detection and RAG

process_persona() strips any [legal ai] prefix and selects the appropriate tool set and system prompt. The embeddings store (if populated) is searched for relevant context. _broadcast_retrieval_context() reports what was found.

Source: the_server.py lines 647–677

Step 4 — Cognition: first LLM call (line 709)

The LLM receives: system prompt + conversation history + RAG context + user question + tool manifest. The model streams its response back as chunks. 

broadcast_trace("cognition", f"Cycle {_ + 1} — reasoning over {len(messages)} messages", session_id)

Step 5 — LLM decides to call get_weather (lines 716–726)

The streamed response contains a function_call delta, not text. The loop assembles the function name and arguments across chunks.

    broadcast_trace("control",
        f"HITL GATE: `{function_call['name']}` requires human approval", session_id)
    return ...   # pauses and waits for POST /approve-tool

When auto_approval is True (the normal demo mode), this gate passes immediately and the next broadcast is APPROVED.

Step 7 — ACTION: execute tool (lines 773–790)

broadcast_trace("action", f"Executing `{function_call['name']}`...", session_id)

    f"Result from `{function_call['name']}` (cycle {_ + 1}):\n{_result_preview[:300]}\n"
    "→ This result will be stored as a Memory Fact", session_id)

Step 8 — MEMORY: fact stored (lines 797–802)

broadcast_trace("memory",
    f"Fact stored after cycle {_ + 1}: `{function_call['name']}` result is now confirmed knowledge.\n"
    f"Value: {_result_preview[:150]}\n"
    "Effect: The LLM will treat this as ground truth in all subsequent reasoning cycles.",
    session_id)

Step 9 — Second LLM call: final answer

The LLM now sees the function result injected as a [Memory Fact] system message. It produces a natural-language answer. The loop detects no function_call and breaks. The response is streamed back to mirror-app/law-ph.

8. The Glass-Box Tracer UI

The tracer UI is a single HTML file served at http://127.0.0.1:8004/ by scl-core-v2's tracer server. It connects to /trace-stream via the browser's native EventSource API and renders each incoming event as a color-coded entry.

Source: run_glass_box_tracer.html

Key UI features

  • Connection status dot — Green when connected, red when disconnected with auto-reconnect. The status line reads "Connected — watching chat-wonder-v2-api R-CCAM events…"
  • Color-coded stage badges — Each R-CCAM stage has a unique color (REQUEST=purple, RETRIEVAL=green, COGNITION=blue, CONTROL=gold, ACTION=orange, MEMORY=light purple)
  • Session filter — All sessions that have produced events are added to a dropdown. Select any session to filter the trace to only that session's events.
  • Clear button — Wipes all entries and resets the session dropdown.
  • Auto-scroll — New events scroll into view automatically.
  • Ping suppression — Keep-alive {"type":"ping"} events are silently discarded and never shown in the UI.

How the browser connects

// run_glass_box_tracer.html — JavaScript
const API_HOST = "http://127.0.0.1:8004";   // scl-core-v2 tracer server

function connect() {
    es = new EventSource(`${API_HOST}/trace-stream`);
    es.onopen  = () => { dot.className = 'dot connected'; ... };
    es.onmessage = (event) => {
        let payload = JSON.parse(event.data);
        if (payload.type === 'ping' || payload.type === 'connected') return;
        trackSession(payload.session_id);
        appendEntry(payload);
    };
    es.onerror = () => { es.close(); setTimeout(connect, 3000); };
}

9. Option 2 — Chain-of-Thought Reasoning (Pending Implementation)

Status: Designed, not yet implemented The code changes described in this section have been planned and reviewed but not yet written. They will be implemented before the VivaTech 2026 demo.

The gap in the current system

The current tracer shows what tool the LLM called and what arguments it constructed. What it does not yet show is why — the LLM's own stated reasoning for choosing that tool over the alternatives.

The COGNITION event currently reads: 

Proposed tool call: `get_weather`
Why this tool: "Returns current weather conditions for a city"   ← tool description, not LLM's reasoning
Arguments passed: {"city": "Manila"}

The "Why this tool" line is taken from the tool's description string, not from the LLM's decision process. We want the LLM to explain its own choice.

Two approaches considered

Option 1 — Background reconstruction Option 2 — Chain-of-thought (chosen)
How After the tool call, launch a separate LLM call: "The AI chose get_weather. Explain why." Instruct the LLM to write one REASON line before its tool call, in the same inference pass
Authenticity Fabricated — a plausible explanation invented after the decision Genuine — the LLM's actual reasoning at the moment of the decision
XAI compliance Fails — a post-hoc explanation can be challenged as fabricated under regulation Compliant — the REASON line is produced before the tool call in the same inference
Latency Adds a full second LLM call per tool call Adds ~20 tokens to the first response; no extra API calls
Cost Doubles LLM API cost for every tool call Negligible — ~20 extra input tokens per tool call

How Option 2 is implemented

Step 1 — Add XAI instruction to the system prompt

Location: the_server.py line ~467 in prepare_chat_messages()

# Append after the existing system_content block is assembled
system_content += (
    "\n\n[XAI Transparency Requirement]\n"
    "When you decide to call a tool, write exactly one line BEFORE the tool call:\n"
    "REASON: <one sentence — why this tool, referencing the user's specific request>\n"
    "Only write a REASON line when calling a tool. Never write it in a text-only response.\n"
    "The REASON line is for system logging only — do not reference it in your answer.\n"
)

The LLM now produces something like: 

REASON: The user asked about current weather in Manila so I need live temperature data.
[function_call: get_weather({"city": "Manila"})]

Step 2 — Extract REASON in run_function_chain (non-streaming)

Location: the_server.py lines ~546–558 after the stream loop

# After the stream loop, before the "if not function_call['name']" check
_xai_reason = None
if last_response:
    _clean_lines = []
    for _ln in last_response.split("\n"):
        if _ln.strip().startswith("REASON:") and _xai_reason is None:
            _xai_reason = _ln.strip()[7:].strip()
        else:
            _clean_lines.append(_ln)
    last_response = "\n".join(_clean_lines).strip()

if _xai_reason and function_call["name"]:
    broadcast_trace("cognition", f"Reasoning: {_xai_reason}", session_id)

Step 3 — Buffer first line in streaming_run_function_chain

The streaming version yields text immediately as chunks arrive. We cannot wait until the stream is complete before checking for a REASON line. Instead, we buffer incoming content until we have one complete line, then decide: if it starts with REASON:, extract it silently; otherwise, yield it to the client.

Location: the_server.py lines ~723–726 (current yield part block)

# Initialise per-cycle state before the stream loop
_xai_buffer = ""
_xai_first_line_done = False
_xai_reason = None

# Inside the stream loop — replace "yield part" with:
elif hasattr(delta, "content") and delta.content:
    part = delta.content.replace("~", "-")
    if not _xai_first_line_done:
        _xai_buffer += part
        if "\n" in _xai_buffer:
            _xai_first_line_done = True
            newline_pos = _xai_buffer.index("\n")
            first_line = _xai_buffer[:newline_pos]
            remainder = _xai_buffer[newline_pos + 1:]
            if first_line.strip().startswith("REASON:"):
                _xai_reason = first_line.strip()[7:].strip()
                # Discard first_line — do NOT yield it to the client
            else:
                last_response += first_line + "\n"
                yield first_line + "\n"
            if remainder:
                last_response += remainder
                yield remainder
            _xai_buffer = ""
    else:
        last_response += part
        yield part

What the tracer will show after Option 2 is implemented

The COGNITION sequence for the Manila weather query will become:

COGNITION14:32:01 Cycle 1 — reasoning over 2 messages (model: gpt-4o-mini)
COGNITION14:32:02 Reasoning: The user asked about current weather in Manila so I need live temperature data from a real-time weather source.
(← This is the LLM's own words, written before calling the tool — authentic XAI evidence)
COGNITION14:32:02 Proposed tool call: `get_weather`

Arguments passed: {"city": "Manila"}
XAI compliance met The "Reasoning:" line appears BEFORE "Proposed tool call" because the LLM wrote it before making the call — in the same inference pass. This is the chronological truth. The tool description line is supplemental context from our metadata; the Reasoning line is the authentic explanation.

What the client (mirror-app / law-ph) sees

Nothing changes from the client's perspective. The REASON line is stripped before it reaches the response stream. The calling application receives exactly the same final answer it always did.

Future: end-user XAI visibility

A single config flag (_context.xai_reason_visible, defaulting to False) controls whether the REASON line is stripped or passed through to the client. When set to True, end users of law-ph or mirror-app would see the AI's reasoning inline. This is ready to be enabled — it is one line change, not a refactor.
