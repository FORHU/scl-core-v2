Option 2: Chain-of-Thought Reasoning

XAI Compliance Plan — chat-wonder-v2-api / scl-core-v2 Glass-Box Tracer
Created: 2026-05-26  |  Status: Pending implementation  |  Open questions: 3

1. Why This Exists

chat-wonder-v2-api is not a chatbot. It is an AI decision engine that powers other apps — mirror-app (the StyleOS smart mirror) and law-ph (Philippine legal AI). Those apps use chat-wonder's R-CCAM loop to make decisions that affect real people: which laws apply to your case, what the mirror should recommend, what actions the AI should take on your behalf.

The EU is enacting XAI — Explainable AI as enforceable law under the EU AI Act. The core requirement: when an AI system makes a decision that affects a person, that person has the right to a genuine explanation of why the decision was made — not a technical log, not a summary written after the fact, but an account of the actual reasoning.

SCL (Supervised Cognitive Loop) and the glass-box tracer are the team's answer to this requirement. The tracer already shows what happens at each R-CCAM stage. What it has not yet shown is why the LLM chose each action — what in the user's specific request or prior context led it to call a particular tool at that moment.

The core problem: The current tracer shows the tool's description as a proxy for "why" — e.g. "Why this tool: Retrieves current weather for a city." That is the tool's general purpose, not the LLM's reasoning for this specific call. A regulator or affected user reading that explanation is not learning anything about why the AI chose this tool for their specific query.

2. Why Option 1 Was Rejected

Option 1 proposed spinning up a background thread that — after the LLM has already decided and executed a tool call — makes a second, separate LLM call asking "why did it choose that tool?" and broadcasts the result.

Option 1 is legally a fabrication. A separate LLM call generating a plausible explanation after the fact is not a record of the AI's reasoning — it is another AI making up a story about what the first AI thought. Under XAI regulation, post-hoc rationalisation is exactly what the law is designed to prevent. An auditor could rightfully reject it: "This explanation was not produced during the decision. It was written afterward by a different process. It does not represent the AI's actual reasoning."

REJECTED  Option 1 — Background Thread

  • Explanation generated after the tool call
  • Written by a separate LLM call
  • Zero latency impact on main loop
  • Plausible but not genuine
  • Not defensible under XAI audit

CHOSEN  Option 2 — Chain-of-Thought

  • Explanation generated before the tool call
  • Written by the same LLM in the same inference
  • Slight latency increase (~20 tokens per tool cycle)
  • Genuine — this is what the LLM was thinking
  • Defensible under XAI audit

3. How Option 2 Works — Plain English

The LLM receives a new instruction as part of its system prompt every time it is called:

"Before calling any tool, write exactly one line starting with REASON: explaining why you are making this call, referencing the user's specific request. Only write a REASON line when calling a tool — never in a text-only response."

When the LLM decides to call a tool, it now produces output that looks like this (as it streams): 

REASON: The user asked about weather in Manila so I need live temperature data.
[function_call → get_weather(city="Manila")]

chat-wonder-v2-api intercepts the REASON: line as it streams in:

  1. It reads the line before it reaches the client (law-ph or mirror).
  2. It broadcasts the reasoning text to the glass-box tracer as a ◈ COGNITION event.
  3. It strips the REASON: line from the response — law-ph and mirror never see it.
  4. The tool call executes as normal. The LLM's final answer to the user is unchanged.

The reasoning text is the LLM's own words, written in the same inference pass as the tool call. It is not reconstructed. It is not approximated. It is what the LLM decided before it acted.

Where: prepare_chat_messages() — lines 428–474. This function builds the message list sent to the LLM on every call. It already handles two cases:

The XAI instruction must be added after both branches — so it applies to both legal and general paths — but before the date context injection. The exact insertion point is after line 461, before the date context line (~line 463):

    "Only write a REASON line when calling a tool. "
    "Never write it in a text-only response.\n"

Why append after both branches? The legal path uses addendum_override loaded from legal_prompt.txt, which completely replaces the generic system prompt. If we only added the XAI instruction inside the if addendum_override block, general queries would not get it — and vice versa. Appending after both ensures universal coverage.

Step 2 — Extract REASON in run_function_chain (non-streaming)

Where: Lines 516–642. This function is called by the /chat (HTTP POST) endpoint.

How the current loop works: The LLM streams its response chunk by chunk. Text content accumulates in last_response. Function call data accumulates in function_call["name"] and function_call["arguments"]. After the loop, the code checks: did we get a function call? If yes, execute it. If no, the text in last_response is the final answer.

The change: After the stream loop ends, before checking if not function_call["name"], scan last_response for a REASON: line. Extract it, broadcast it to the tracer, and remove it from last_response so the client never sees it.

Why "only broadcast if a tool call follows"? The LLM might occasionally write a REASON: line even when giving a text-only response (prompt instructions aren't perfectly obeyed 100% of the time). If there's no tool call, the REASON is spurious and should not appear in the tracer — it would be misleading.

Step 3 — Extract REASON in streaming_run_function_chain (generator)

Where: Lines 685–803. This function is called by the /chat-stream WebSocket endpoint. It is a Python generator — it yields content chunks as they arrive (yield part on line 723).

The problem: In the non-streaming version, we can wait for the full loop to finish and then scan last_response. Here, text is yielded immediately to the client chunk by chunk. If we yield the REASON: line before we've identified it, the client (law-ph, mirror) would see it.

The solution — first-line buffering: We buffer incoming text until we have one complete line (terminated by \n). We check that first complete line:

  • If it starts with REASON: — extract the text, broadcast to tracer, discard (don't yield to client). Then resume yielding normally for all subsequent content.
  • If it does not start with REASON: — flush the buffered content to the client immediately, then resume yielding normally.

This means we only buffer the minimum amount of text needed to inspect the first line. Once that decision is made (REASON or not), streaming to the client continues at full speed. For tool-calling cycles, the REASON line is the only text content produced before the function call — so after discarding it, the stream has nothing left to yield until the next cycle anyway.

Initialise these variables at the top of the for _ in range(max_chains): loop body:

_xai_buffer = ""          # accumulates text until first \n is found
_xai_first_line_done = False  # True once we've inspected the first line
_xai_reason = None         # holds the extracted REASON text if found

Replace the content chunk handler (current line 720–723) with:

elif hasattr(delta, "content") and delta.content:
    part = delta.content.replace("~", "-")

    if _xai_first_line_done:
        # First line already decided — yield normally
        last_response += part
        yield part

    else:
        # Still buffering — waiting for first complete line
        _xai_buffer += part

        if "\n" in _xai_buffer:
            _xai_first_line_done = True
            newline_pos = _xai_buffer.index("\n")
            first_line = _xai_buffer[:newline_pos]
            remainder  = _xai_buffer[newline_pos + 1:]

            if first_line.strip().startswith("REASON:"):
                # Extract — do NOT yield to client
                _xai_reason = first_line.strip()[7:].strip()
            else:
                # Not a REASON line — flush to client
                last_response += first_line + "\n"
                yield first_line + "\n"

            # Flush any text that followed the first line on the same chunk
            if remainder:
                last_response += remainder
                yield remainder
            _xai_buffer = ""

After the stream loop, broadcast if a tool call followed:

6. What law-ph and mirror Actually Receive

The REASON: line is intercepted and stripped before the response reaches the client. The apps receive exactly what they received before this change — the LLM's final answer, clean and unchanged.

7. The Legal AI Path — A Separate Problem

The [legal ai] persona prefix routes queries to a completely different code path: run_legal_persona_ask() → legal_rag_ask(). This path:

  • Does a pgvector similarity search to retrieve relevant Philippine laws
  • Passes the retrieved laws as context to a single, non-streaming LLM call
  • Returns the LLM's synthesised answer with citations
  • Never enters the tool loop at all — there are no tool calls, so there are no REASON: lines

Option 2's chain-of-thought mechanism will have zero effect on the legal path. The REASON instruction in the system prompt will never trigger because no tool call is made.

The legal path needs its own XAI mechanism — different from the tool-call REASON approach. The most important explainability question for law-ph is: why were these specific statutes selected and applied to this query? Relevance scores alone are not sufficient; a legal user deserves to know what in their question matched what in the law.

This is out of scope for the current implementation but is a required follow-up. The legal path's XAI explanation needs to be planned separately.

8. Open Questions — Grilling Points

OPEN QUESTION 1 — Most Important

Should the REASON text be shown to end users (law-ph users, mirror users) or remain tracer-only?

The EU AI Act's right to explanation is about informing affected individuals, not developers. Stripping REASON from the client and keeping it in a developer dashboard satisfies internal monitoring but may not satisfy the user-facing transparency requirement.

If shown to users: no stripping needed — law-ph and mirror receive the REASON line as part of the AI's response text. Much simpler implementation. But requires law-ph and mirror to render it appropriately (not just dump it inline).

If tracer-only: current plan — strip from client, broadcast to SSE only. Simpler for the client apps, but the compliance story is weaker.

Recommendation: show to end users. The regulation targets them, not the tracer.
OPEN QUESTION 2

Should REASON text be persisted (logged to a database) or only broadcast over SSE?

SSE is ephemeral — if the tracer tab is closed, or the connection drops, or the server restarts, the reasoning is lost. For a real XAI audit trail, you need a durable record: who asked what, what the AI decided, what its reasoning was, when.

Persistence means writing to the existing PostgreSQL database (alongside session_id and timestamp) every time a REASON is extracted. This is additional scope but may be required for compliance.

Recommendation: log to DB. SSE-only is sufficient for development; compliance requires durable records.
OPEN QUESTION 3

What is the plan for the legal AI path's XAI requirement?

law-ph is arguably the highest-stakes context for XAI — legal decisions directly affect people's rights. The current plan leaves the legal path without genuine reasoning explanations. The citation display shows which laws were retrieved but not why they apply to this specific query.

Recommendation: plan a separate legal-path XAI mechanism — likely asking the LLM to explain each cited statute's relevance inline in the synthesised answer.
